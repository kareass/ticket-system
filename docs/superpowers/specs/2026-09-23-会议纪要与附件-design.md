## 二、数据模型

两张新表，**纯新增**。迁移只含 `CREATE TABLE`，不含任何 `RedefineTables` 重建，
不动现有数据 —— 与上一次 `Requirement` 表重建的迁移相比，风险低一个量级。

### 2.1 Meeting

```prisma
model Meeting {
  id          String   @id @default(cuid()) // 内部主键
  date        DateTime // 日期（必填，日期选择器默认当天）
  title       String   // 主题（必填）
  attendees   String?  // 参会人（JSON 数组文本，如 ["张三","李四"]）
  recorder    String?  // 记录人
  content     String?  // 会议内容
  attachments MeetingAttachment[]
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  @@map("Meeting")
}
```

### 2.2 MeetingAttachment

```prisma
model MeetingAttachment {
  id         String   @id @default(cuid()) // 内部主键
  meeting    Meeting  @relation(fields: [meetingId], references: [id], onDelete: Cascade)
  meetingId  String
  fileName   String   // 原始文件名（仅用于展示与下载时的文件名）
  storedName String   @unique // 磁盘上的文件名（服务端生成，见 3.2）
  size       Int      // 字节数
  mimeType   String?  // 上传时的 content-type（仅作参考，不用于安全判断）
  createdAt  DateTime @default(now())

  @@map("MeetingAttachment")
}
```

`onDelete: Cascade` 让删除纪要时附件**记录**自动清掉；**磁盘文件由应用层删除**（见 3.3）。

### 2.3 为什么参会人存 JSON 数组而不是顿号分隔串

`attendees` 是一个**列表**，SQLite 没有数组类型。两种存法：

| 存法 | 问题 |
|------|------|
| `"张三、李四"` | 含义完全依赖「人名里不含顿号」这一假设，假设破了就**静默错**：一个人被读成两个人 |
| `["张三","李四"]` | 结构上就分得清，无假设 |

选 JSON。代价是多一步解析，**解析失败必须回退成空数组而不是抛错**（见第六节）。

**出参一律经过 `toMeetingJson` 归一**：库里存字符串，接口出去的是 `string[]`，
前端不需要知道存储细节。

## 三、附件

### 3.1 存储位置与磁盘布局

- 目录：`<项目根>/uploads/`（`.gitignore` 须加 `/uploads`）
- 布局：**平铺**，`uploads/<storedName>.<ext>`，不按纪要建子目录

平铺的理由：定位文件靠数据库记录（`storedName` 唯一），不依赖目录结构；
建子目录反而多一层「目录与记录不同步」的可能。

### 3.2 原始文件名与磁盘文件名必须分离（**本方案的关键安全点**）

`file.originalname` 是**用户可控输入**，可能是：

- `../../.env`（路径穿越）
- `截图 2026/09/23.png`（含路径分隔符）
- `CON`、`NUL`（Windows 保留设备名）
- 超长文件名、`\0` 截断

**绝不能**拿它拼磁盘路径。规则：

1. `storedName` 由服务端生成：`crypto.randomUUID()`，**不含任何用户输入**
2. 扩展名取 `originalname` 的最后一个 `.` 之后的部分，转小写，**比对白名单**，不在白名单则 400
3. 最终路径用 `path.join(UPLOAD_DIR, storedName + ext)`，并在写入前断言
   `path.dirname(结果) === UPLOAD_DIR`
4. `originalname` 只存进数据库 `fileName`，用于展示和下载时的文件名

**后缀白名单**（不分大小写）：

```
图片    .png .jpg .jpeg .gif .webp .bmp
文档    .pdf .doc .docx .xls .xlsx .ppt .pptx
文本    .txt .csv
压缩包  .zip .rar .7z
```

**不用 `mimeType` 做安全判断** —— 它同样来自客户端，可以随便伪造。它只存下来作参考。

### 3.3 上传 / 下载 / 删除的行为

**上传** `POST /api/meetings/{id}/attachments`（multipart/form-data，字段名 `file`）

1. 校验纪要存在，否则 404
2. 校验后缀白名单，否则 400
3. 校验大小 ≤ 20MB，否则 400
4. 写盘 → 写数据库记录 → 返回记录（含 `id` / `fileName` / `size`）
5. 任一步失败：**先删掉可能已写盘的半截文件**，再返回错误，不留垃圾

**下载 / 预览** `GET /api/attachments/{id}`

- 记录不存在 → 404
- **记录在但文件不在** → 404 并给出明确文案（不要 500，也不要静默返回空文件）
- 图片 → `Content-Disposition: inline`（页面里 `<img src>` 直接能用）
- 其他 → `Content-Disposition: attachment`（触发下载）
- **中文文件名必须用 RFC 5987 双写**：
  `Content-Disposition: attachment; filename="fallback"; filename*=UTF-8''%E4%BC%9A%E8%AE%AE.pdf`
  —— 只写 `filename=` 的话中文名在浏览器里会变乱码或被截断

**删除单个附件** `DELETE /api/attachments/{id}`

- 先删数据库记录，**再**删磁盘文件；文件删除失败只记日志，不返回错误
  （理由见下）

**删除纪要** `DELETE /api/meetings/{id}`

1. 查出该纪要所有附件的 `storedName`
2. `prisma.meeting.delete()` —— 附件记录随 `onDelete: Cascade` 一并清掉
3. **事务提交之后**，再逐个 `unlink` 磁盘文件；失败只记日志

> **为什么先删记录、后删文件**：反过来（先删文件再删记录）一旦第二步失败，就会留下
> 「记录还在、文件没了」的状态 —— 用户在列表里看得到附件、点开却打不开，且**无法自行修复**。
> 而先删记录后删文件，最坏情况是留一个孤儿文件，它占几十 KB、不影响任何人、可事后清理。
> 两害相权，选可恢复的那个。

### 3.4 本方案不覆盖的场景（明确说明，避免误解）

- **不是流式校验**：服务端会先看 `Content-Length`（超限直接 413），再用
  `request.formData()` 取文件后校验 `file.size`。但 `formData()` 会把整个 body 缓冲完
  才交给代码 —— 也就是说一个超大请求仍会被 Node 读进内存后才被拒绝。**单用户内网场景
  可接受**；若将来要开放给更多人，须改为流式 multipart 解析并边读边断。
- **不做**：断点续传、秒传、病毒扫描、附件内容索引、在线编辑。

## 四、备份与部署的连带改动（附件的真正成本）

**这是本方案最容易被低估的部分。** 项目当前的备份模型是「一个 `.db` 文件 = 全部数据」，
这条假设被附件打破，且**是静默打破的** —— `npm run db:backup` 不会报错、不会提示，
但产物不再包含附件。不处理的话，用户会以为备好了。

| 文件 | 改动 |
|------|------|
| `scripts/backup-db.mjs` | 产物由 `backups/<时间戳>.db` 改为 `backups/<时间戳>.tar.gz`，内含 `dev.db` 快照 + `uploads/` 全目录 |
| `.gitignore` | 新增 `/uploads` |
| `docs/内网部署方案.md` | 整包投递的 `tar` 命令**必须加 `--exclude=uploads`**，否则会把开发机/准备机上的附件带到目标机 |
| `docs/部署指南.md` | 备份与回滚章节改写；第八节「部署机 ≠ 开发机」的不可复制清单**加上 `uploads/`** |
| `docs/内网部署方案.md` 第九节 | 「一个文件即全部数据」的表述需修正 |

**备份实现要点**：

- 第一步仍用 `VACUUM INTO` 生成一致性快照（现成逻辑，不重写），落到临时路径
- 第二步用**系统自带的 `tar`** 把快照 + `uploads/` 打成 `.tar.gz`，然后删掉临时快照
  —— **不新增 npm 依赖**；`tar` 在内网投递文档里已经在用，Windows 10 自带
- `uploads/` 不存在时（尚无任何附件）**必须能正常备份**，不能报错
- 保留策略 `BACKUP_KEEP`（默认 30）的清理正则需同时认旧 `.db` 与新 `.tar.gz`，
  否则升级后旧备份永远不会被清理
- ⚠️ 打包 `uploads/` 时**若正好有文件在上传**，可能打进半截文件。单用户场景基本不会遇到，
  但需在脚本注释中写明该前提

## 五、接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/meetings` | 列表，支持 `keyword`（搜主题/参会人/记录人/内容）与 `attendee`（按人筛） |
| POST | `/api/meetings` | 新建（JSON，**不接收文件**） |
| GET | `/api/meetings/{id}` | 单查（含附件列表） |
| PUT | `/api/meetings/{id}` | 编辑 |
| DELETE | `/api/meetings/{id}` | 删除（连带附件记录与文件） |
| POST | `/api/meetings/{id}/attachments` | 上传附件（multipart） |
| GET | `/api/attachments/{id}` | 下载 / 预览 |
| DELETE | `/api/attachments/{id}` | 删除单个附件 |

沿用项目既有约定：每个 route handler `export const runtime = "nodejs"`；
Next 14 的 `params` 是**同步对象**（`{ params }: { params: { id: string } }`，不要 `await`）；
共享工具一律从 `src/lib/server/helpers.ts` 取。

**PUT 的三态语义**（与需求模块一致，不得自创）：

- `undefined`（未传）→ 不改该字段
- `""`（显式清空）→ 落 `null`
- 非空 → 改

**「参会人」在 PUT 里的额外约定**：传数组 `["张三"]` 则整体替换；
传 `[]` 视为清空；未传则该字段不动。**不做数组级增量合并**（语义不清，容易出意外）。

**`GET /api/meetings` 的 `keyword` 搜索范围**：`title` / `recorder` / `content` 用 `contains`；
`attendees` 是 JSON 文本，用 `contains` 直接匹配子串即可（`"张三"` 能命中 `["张三","李四"]`，
**也可能命中** `["张三丰"]` —— 这是已知的近似匹配，见第十节「不做」）。

## 六、错误处理

| 情况 | 响应 |
|------|------|
| 主题为空 / 非字符串 | 400 |
| 日期缺失或非法日历日 | 400 |
| 纪要 id 不存在 | 404 |
| 附件后缀不在白名单 | 400，文案说明允许的类型 |
| 附件超过 20MB | 两道关，**用不同状态码区分**：① `Content-Length` 预检超限 → **413**（在读取 body 前就拒绝）；② 预检通过但实际 `file.size` 超限 → **400** |
| 上传时磁盘写入失败 | 500，且**已写入的半截文件必须删掉** |
| 下载时记录在、文件不在 | 404 + 明确文案，**不是** 500 |
| `attendees` JSON 损坏（脏数据） | **回退成 `[]`**，不抛错、不 500 |
| 删文件的 unlink 失败 | 只记日志，**不影响接口返回** |

前端统一走既有的 `toErrorMessage`。

## 七、前端

### 7.1 页面

| 路径 | 内容 |
|------|------|
| `/meetings` | **只读列表**：日期 / 主题 / 参会人 / 记录人 / 会议内容（超长省略）/ 操作（编辑·删除） |

- 工具栏：关键词搜索 + 刷新 + 新建；表头双击排序沿用 `SortableHeader`；前端分页 10 条/页
- 排序：日期默认倒序，其余列按现有 `sortRows` 口径

### 7.2 组件

| 文件 | 说明 |
|------|------|
| `src/components/MeetingForm.tsx` | 新建/编辑共用表单；主题必填、日期默认当天 |
| `src/components/common/PersonSelect.tsx` | **新增公共组件**：可自由输入 + 从候选里点选 |

**`PersonSelect` 的候选人名来源**：已加载的全部纪要中 `attendees` 与 `recorder` 出现过的
人名去重。项目 store 持有**全量**纪要（分页在前端做），因此候选是完整的，**不需要新接口**。
参会人用多选模式，记录人用单选模式。

### 7.3 附件交互

- 编辑页显示已有附件：图片出缩略图，其余出「文件名 + 大小 + 删除按钮」
- **新建时选中的文件先留在浏览器内存，点保存才上传**：
  1. 先按 JSON 建纪要，拿到 `id`
  2. 再逐个 `POST` 附件
- **上传失败必须明说**：提示「纪要已保存，但有 N 个附件上传失败，请到编辑页重新上传」，
  **不得假装成功**

> 这样设计是为了让 `POST /api/meetings` 保持与其它模块一致的**纯 JSON** 形态，
> 不必为了附件把创建接口改成 multipart。

## 十、明确不做

- **不关联工单/需求** —— 用户明确选择「两个功能各自独立，互不相关」
- **不产生待办、不触发提醒** —— 同上
- **不做内联编辑** —— 会议内容为长文本，部分字段可改、部分不可改会造成心智负担
- **不记会议时间（时刻）** —— 全站日期字段均为「日历日」口径，不为此开特例
- **不做**：附件分类/文件夹、断点续传、病毒扫描、会议地点、会议类型、草稿/定稿状态
- **不做权限控制** —— 系统无账号体系
- **不精确匹配参会人** —— `keyword` 搜 `attendees` 是子串近似匹配（搜「张三」会命中「张三丰」）；
  真正的按人精确筛选是 `attendee` 参数的职责，但它同样是子串匹配，本版不做 JSON 内部的精确解析
- **不改** `work-order-sync.ts` 及任何现有接口契约

## 十一、已知的既有事实（供实施者参考）

- 项目**目前完全没有文件处理能力**：`src/` 下无任何 `formData` / `writeFile` / `fs` 调用。
  `src/lib/server/attachments.ts` 会是本项目第一个文件 IO 模块
- 现有列表页 `src/app/work-orders/page.tsx`（434 行）与 `src/app/requirements/page.tsx`（403 行）

  这一段。**本方案不抽取该公共层** —— 那是独立重构，不在本次范围

- 项目用 `prisma migrate deploy` 应用迁移；生成迁移用 `prisma migrate dev`
  （⚠️ 若出现**交互式「是否重置数据库」提示，必须中止并回报**）
- `scripts/backup-db.mjs` 现有产物为 `backups/YYYYMMDD-HHMMSS.db`，清理正则为 `/^\d{8}-\d{6}\.db$/`

## 十三、实现顺序建议

本 spec 明显大于项目前几轮的单点改动，建议**分两阶段**：

| 阶段 | 内容 | 交付 |
|------|------|------|
| 一 | 会议纪要 CRUD（数据模型 → 接口 → 页面 → 冒烟） | **此时你就能开始用** |
| 二 | 附件（存储层 → 上传/下载/删除 → 备份改造 → 文档） | 在阶段一稳定后叠加 |

理由：附件失败或延期**不影响纪要主体可用**；且阶段一先跑通能提前暴露数据模型问题，
避免把附件建在错误的模型上。
