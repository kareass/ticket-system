## 一、目标与范围

新增一个**完全独立**的「工作提醒」模块：登记「什么时候要提醒谁做什么」，并跟踪是否办结。

| 项 | 决定 |
|----|------|
| 字段 | 日期 / 提醒人 / 提醒内容 / 是否已完成 |
| 提醒人 | **固定下拉**，取值来自 `src/types/index.ts` 的 `REMINDEE_OPTIONS`，**必填** |
| 提醒内容 | **必填**，不可为空 |
| 列表交互 | **只读列表**（不做内联文本编辑）+ 独立新建/编辑页；**唯一例外见下** |
| 勾选「已完成」 | **点即落库，不经草稿门** —— 全站唯一一处不显式提交的写入 |
| 日期 ≤ 今天且未完成 | **整行文字标红** |
| 与其它模块的关系 | **无**。不关联工单/需求/会议，不产生派生待办，不主动外发通知 |

**这是新增模块，不是修改现有业务** —— 不碰 `WorkOrder` / `Requirement` / `Meeting` 三张表，
不改 `work-order-sync.ts`，不改任何现有接口的契约。

### 1.1 为什么「勾选即保存」要破全站规则

项目硬规则第 2 条是「修改需显式提交，不做自动保存」，其目的在
`src/lib/useRowDrafts.ts` 里写得很清楚：**防止用户填了一半的文本被静默丢弃**。

「已完成」是一个**布尔开关，没有中间态** —— 点一下就是最终意思，再点一下退回未完成。
草稿门要防的那种「半成品被静默丢掉」在这里不可能发生。因此本模块**唯一一处**破例：
列表里的完成勾选直接 `PUT`。

⚠️ 破例范围**严格限定**在 `isDone` 这一个布尔字段。列表上的文本字段（提醒内容）**不做内联编辑**，
要改就进编辑页 —— 那才是需要草稿门保护的东西。

### 1.2 本模块不做主动推送（重要，避免误解）

「提醒」在本模块里的含义是**打开页面时看得见的待办标记**，不是**主动送达的通知**。
系统没有账号体系（不知道发给谁）、部署在内网（不出网）、也没有任何后台定时进程。
设计方案第八部分 Phase 2 列的「邮件通知和提醒」**不在本次范围**（见第九节）。

> 按项目硬规则「明确列举取值的属于需求变更，应先改文档」，本模块在
> `docs/四川物流工单系统-设计方案.md` 中**完全没有记载**，实施前须先在该文档补上
> 「数据模型」一张表与「核心功能清单」一行（见第八节）。**只做前向追加，不动任何现有口径。**

## 二、数据模型

### 2.1 Reminder

```prisma
model Reminder {
  id        String   @id @default(cuid())
  date      DateTime                    // 提醒日期（按日历日入库，表单默认今天）
  remindee  String                      // 提醒人（REMINDEE_OPTIONS 之一；必填）
  content   String                      // 提醒内容；必填
  isDone    Boolean  @default(false)    // 是否已完成
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  @@map("Reminder")
}
```

### 2.2 为什么 `remindee` 是**非空**，而 `submittedBy` 是可空

`WorkOrder.submittedBy` / `Requirement.submittedBy` 用 `String?`，是因为那两个字段是
**在既有表上加的**，库里已有历史记录没有值，接口层只能「新记录必填、历史数据放行」。

`Reminder` 是**全新的表，不存在历史数据**，因此把「必填」直接落到库结构（`String` 非空），
比「可空 + 接口层校验」更强：数据库层面就不可能存进一条没有提醒人的提醒。
`content` 同理。

### 2.3 日期口径（项目铁律，不得违反）

与全站一致，一律按**日历日**处理：

- 入库：`new Date(dateStr + "T00:00:00.000Z")`
- 出参：`date.toISOString().slice(0, 10)`
- **绝不用** `new Date(dateStr)` —— `+8` 时区会让日期偏一天（`helpers.ts` 的
  `toDayUtc` / `toDayStr` 已是现成实现，直接用）。

### 2.4 迁移

新增列**必须**跑一次迁移（与会议纪要那次一样，`isDone` 是新表的列）：

```bash
npx prisma migrate dev --name add_reminder
```

迁移文件名形如 `prisma/migrations/<时间戳>_add_reminder/migration.sql`。
**不要在 dev server 运行时跑** —— Windows 上会 EPERM（`.next` / Prisma 引擎被锁），先停服。

## 三、接口

四个路由，全部照抄工单/需求/会议纪要的既定形状：`export const runtime = "nodejs"`、
Next 14 的 `params` 是**同步对象**（不要 `await`）、错误响应 `{error, details?}`。

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/reminders` | 列表，支持筛选下推 |
| `GET` | `/api/reminders/{id}` | 单查 |
| `POST` | `/api/reminders` | 新建 |
| `PUT` | `/api/reminders/{id}` | 局部更新（含勾选完成） |
| `DELETE` | `/api/reminders/{id}` | 删除 |

### 3.1 列表 · `GET /api/reminders`

可选查询参数，三者可叠加：

| 参数 | 语义 |
|---|---|
| `?isDone=false` | **三态**：不传 = 全部；`true` / `false` = 只看已完成 / 只看未完成。非法值（如 `?isDone=abc`）视作**不过滤**，不报错 |
| `?remindee=黄傲` | 按提醒人**精确匹配**。值不在 `REMINDEE_OPTIONS` 内时**视作不过滤**（不报错、返回全量）—— 与工单/需求的 `submittedBy` 筛选**同一口径**，不要在这里自作主张改成返回空数组 |
| `?keyword=xxx` | 子串匹配**提醒内容**（忽略大小写） |

> ⚠️ 「非法值不过滤」是本项目接口层的一贯口径（`submittedBy` / `currentNode` 都这样）：
> 筛选参数是**锦上添花**，参数写错时宁可多给数据，也不要让用户面对一个空列表却不知为何。
> 新增筛选参数时照此办理。

**排序：按 `date` 升序，同日按 `createdAt` 升序。**

> ⚠️ **这是全站唯一一个不按 `createdAt` 倒序的列表**（工单/需求/会议三个列表都是倒序）。
> 破例理由：提醒的价值在「接下来要做什么」，最早的日期排最前，已逾期/今日到期的自然浮到顶部。
> 实施时**不要**为了「保持一致」把它改成倒序 —— 那是把最需要看的东西压到最后一页。

响应：`200` → `Reminder[]`

### 3.2 单查 · `GET /api/reminders/{id}`

响应：`200` → `Reminder`；`404` 不存在

### 3.3 新建 · `POST /api/reminders`

```jsonc
{
  "date": "2026-10-13",   // * 必填，YYYY-MM-DD，按日历日入库
  "remindee": "黄傲",      // * 必填，须在 REMINDEE_OPTIONS 内
  "content": "催一下 WMS 出库单打印的验收"  // * 必填，非空
}
```

响应：`201` → `Reminder`；`400` 校验失败（附 `details`）

### 3.4 更新 · `PUT /api/reminders/{id}`

请求体：上述字段的任意子集。

| 字段 | 语义 |
|---|---|
| `isDone` | 传布尔值即设为该值（`false` 也是有效值，**不是**「不改」） |
| `date` | 传则改，须为合法日历日 |
| `remindee` | **不传 = 不改**；传空串 → `400`（必填字段不可清空）；传非空且不在枚举内 → `400` |
| `content` | **不传 = 不改**；传空串 → `400`（必填字段不可清空） |

⚠️ **必填字段不适用三态语义**。项目里「未传 = 不改 / 空串 = 清空 / 非空 = 设为该值」这套三态，
只对**可选**字段成立（`WorkOrder.remark`、`Meeting.recorder`、`submittedBy` 等）。
`remindee` 与 `content` 是必填，空串只能是**用户的误操作或前端 bug**，一律 `400` 打回去。

响应：`200` → `Reminder`；`400` 校验失败 / 无可更新字段；`404` 不存在

### 3.5 删除 · `DELETE /api/reminders/{id}`

响应：`204`；`404` 不存在

### 3.6 没有 409

本表**没有任何唯一性约束** —— 同一天、同一个人、同样的内容，可以有多条提醒（这是合理的：
「催一下打印验收」和「催一下打印验收」可能是两件不同的事）。
因此本模块**不产生 `409`**，也不涉及 `isPrismaUnique`。实施时若发现自己在写 `409` 分支，
说明理解偏了。

## 四、错误处理

| 状态码 | 触发条件 |
|---|---|
| `400` | 缺 `date` / `remindee` / `content`；`date` 非合法日历日（如 `2026-02-30`）；`remindee` 不在枚举内；PUT 用空串清空必填字段；PUT 无任何可更新字段；请求体非 JSON |
| `404` | 目标记录不存在 |
| `204` | 删除成功（无响应体） |

实现约定：

- 校验失败一律附 `details`（字符串数组），逐字段说明问题 —— 与现有接口一致。
- 事务**不需要** —— 本模块是单表操作，没有跨表同步。不要为了「跟工单一样」而套 `$transaction`。
- 空值判断用 `helpers.ts` 的 `asTrimmed`：**非字符串 → `undefined`（不传）**，
  **字符串 → trim 后的值（可能是 `""`）**。这正是「未传」与「传了空串」能区分开的原因，
  也是必填字段能对空串报 400、而不是笼统报「缺字段」的原因。

## 五、前端

### 5.1 页面

| 路由 | 页面 |
|---|---|
| `/reminders` | 列表（只读 + 勾选完成 + 筛选） |
| `/reminders/create` | 新建 |
| `/reminders/edit/[id]` | 编辑 |

三个页面与会议纪要的三个页面**同构**，以 `src/app/meetings/**` 为模板照抄骨架。

### 5.2 列表页 `/reminders`

以 `src/app/meetings/page.tsx` 为模板（只读列表 + 独立编辑页），列定义：

| 列 | 内容 | 宽度 |
|---|---|---|
| （无标题） | `Checkbox`，勾选/取消勾选「已完成」，**点即 PUT 落库** | 50，`align: center` |
| 日期 | `YYYY-MM-DD`，可双击列头排序 | 110 |
| 提醒人 | 名字 | 110 |
| 提醒内容 | 文本，`ellipsis: true` | 自适应 |
| 操作 | 「编辑」（`Link` 到编辑页）/「删除」（`Popconfirm`） | 150，`fixed: right` |

**整行标红的规则**：

```tsx
// 条件：未完成 且 日期 ≤ 今天
// date 是 "YYYY-MM-DD" 字符串，字典序比较即日期序，不必转 Date；
// today() 复用 src/lib/utils.ts 的现成实现（dayjs，返回 "YYYY-MM-DD"）
rowClassName={(r) => (!r.isDone && r.date <= today() ? "reminder-row-overdue" : "")}
```

```css
/* src/app/globals.css —— 追加在文件末尾 */
/* 工作提醒：日期 ≤ 今天且未完成 → 整行红。
   勾选框与「编辑/删除」链接按钮有各自的配色，不受 color 继承影响，保持原样。 */
.reminder-row-overdue > td {
  color: #ff4d4f;
}
```

> 只标红**整行的文字**，不做「今日」与「已逾期」的区分 —— 这是需求方的明确要求（两者同一条规则）。
> 若日后要区分，只需在此规则旁再加一条更深的颜色类，不必改数据结构。

**工具栏**（左侧/右侧两组，照搬会议纪要的 `flex-wrap` 布局）：

- 左：「新建提醒」（`Button type="primary"`）
- 右：「刷新」（`force=true` 重新拉取）、完成状态下拉、提醒人下拉、关键词输入框

**筛选在**前端**做**（与会议纪要列表一致：数据一次拉全量、本地过滤），
**但接口的 `?isDone` / `?remindee` / `?keyword` 参数照常实现**并写进接口文档与冒烟断言 ——
两者都要有：接口是契约，前端过滤是当下最省事的实现。

- **完成状态**：`Segmented`，三档「未完成 / 全部 / 已完成」，**默认「未完成」**
- **提醒人**：普通 `Select` + `allowClear`，选项即 `REMINDEE_OPTIONS`。
  **与工单/需求列表「按提交人筛选」那个下拉保持同样的做法**（不要用 `PersonSelect`）
- **关键词**：`Input` + `SearchOutlined`，`allowClear`，子串匹配提醒内容

**排序**：列头双击沿用 `SortableHeader`（升序 → 降序 → 取消）。
**无排序状态时保持接口返回的 `date` 升序**，前端不重新排序。

**分页**：`pageSize: 10`、`showTotal` —— 与其它三个列表一致。
**横向滚动**：`scroll={{ x: 1000 }}` —— 操作列是 `fixed: "right"`，**不给 `scroll.x` 会让它错位**
（会议纪要列表用的是 `x: 1200`，本表列更少，取小一点即可）。
**列布局持久化**：`layoutStorageKey="reminders"`（`ProTable` 会写 localStorage，每张表一个 key）。
**行 key**：`rowKey="id"`。

### 5.3 组件 `src/components/ReminderForm.tsx`

- 字段：日期（`DatePicker`，**默认今天**）/ 提醒人（`Select`，选项 `asSelectOptions(REMINDEE_OPTIONS)`，必填）/ 提醒内容（`Input.TextArea`，必填）
- 控件宽度按选项文案取固定值（照 F1 验收反馈的做法：不要一律撑满表单宽）
- 复用 `MeetingForm` 的提交/取消按钮区与 `submitting` 态处理
- **编辑页必须从 store 派生数据，不得存 `useState` 快照** —— 见 5.6

### 5.4 首页卡片 `src/app/page.tsx`

现首页是**一组纯静态卡片**（`featureCards` 数组，完全不读 store）。新增第 4 张：

- 标题「工作提醒」，图标 `BellOutlined`，`href="/reminders"`
- 描述行显示「未完成 N 条」；**N 为 0 时显示普通文案**（如「登记待办提醒，到日子一眼看到」）
- 为此首页需要读 store：`useEffect` 里调 `loadReminders()`（走 store 的「已加载」缓存，
  已加载则不重复请求），在组件内用 `useMemo` 数出 `reminders.filter(r => !r.isDone).length`
- **不新增计数接口** —— 数据量小，单开一个 `count` 路由是多余的路由

> ⚠️ antd 陷阱（项目已有记录）：`Form.useWatch` / store 的首次渲染可能拿到空值。
> 卡片文案需要容忍 `remindersLoaded === false` 的短暂状态，**不要**显示「未完成 0 条」
> 再跳成「未完成 3 条」——未加载时显示普通文案即可。

### 5.5 导航 `src/components/layout/RootLayoutClient.tsx`

`menuItems` 数组加第 4 项：

```tsx
{
  key: "/reminders",
  icon: <BellOutlined />,
  label: <Link href="/reminders">工作提醒</Link>,
},
```

`selectedKey` 是按 `startsWith` 现算的，子路由（`/reminders/create` 等）会自动选中，
**那段逻辑不用动**。

### 5.6 store `src/store/store.ts`

新增的状态与动作（与 `meetings` 切片同构）：

| 成员 | 用途 |
|---|---|
| `reminders: Reminder[]` | 列表数据 |
| `remindersLoaded: boolean` | 「已加载」缓存标记，页面来回切换不重复请求 |
| `remindersLoading: boolean` | 加载态 |
| `loadReminders(force?)` | 拉取；`force=true` 时忽略缓存标记（工具栏「刷新」走这条） |
| `addReminder(input)` | 新建，返回创建出的记录 |
| `upsertReminder(r)` | **单查得到的记录并入列表缓存**（编辑页回源后调用） |
| `updateReminder(id, patch)` | 局部更新；**列表勾选完成与编辑页保存共用这一条路径** |
| `deleteReminder(id)` | 删除 |

**`upsertReminder` 必须与 `updateReminder` 同时存在，不能只留后者** —— 这是会议纪要模块
踩过的坑：`updateReminder` 若只对**已在缓存里**的记录做 `.map()` 打补丁，那么编辑页走
「缓存未命中 → `GET /api/reminders/{id}` 单查」这条路径时，数据从未进过 store，
更新会被**静默丢掉**（提示成功但页面无变化）。会议纪要的修复是加 `upsertMeeting`
并让编辑页从 store 派生，本模块**一开始就这么写**。

### 6.4 `src/types/index.ts` 的确切改法

按项目硬规则，**下拉选项只有一个来源**，必须加在这个文件里，不得在任何组件里就地写数组：

```ts
/**
 * 工作提醒的「提醒人」
 * 取值与 SUBMITTER_OPTIONS 相同（同一个部门的两个人），但**各自独立一份**：
 * 「提交人」是**谁登记了这条记录**，「提醒人」是**这条提醒要提醒谁**，语义不同，
 * 日后两份名单可能分化（例如提醒人扩到全员、提交人仍只有登记员）。
 * 合并成一份会在分化那天被迫改成结构性改动。
 */
export const REMINDEE_OPTIONS = ["黄傲", "陈婷婷"] as const;
export type RemindeeValue = (typeof REMINDEE_OPTIONS)[number];
```

以及（放在文件末尾「会议纪要」一节之后）：

```ts
// ---------- 工作提醒 ----------

export interface Reminder {
  id: string;
  /** 提醒日期（日历日 YYYY-MM-DD，表单默认今天） */
  date: string;
  /** 提醒人（REMINDEE_OPTIONS 之一；必填） */
  remindee: string;
  /** 提醒内容（必填） */
  content: string;
  /** 是否已完成 */
  isDone: boolean;
  createdAt: string;
  updatedAt: string;
}
```

> 这两个数组/类型是 `as const` + `typeof ARR[number]` 推导的既有模式，**不要**手写联合类型。
> `REMINDEE_OPTIONS` **不需要配色表** —— 它不像工单状态/需求节点那样在列表里以彩色 Tag 呈现，
> 只是一个下拉与一列纯文本。

### 7.2 中文断言的写法（本项目必须遵守）

⚠️ **绝不在命令行里直接敲中文发请求** —— Windows 控制台按 GBK 处理，到达 `curl` 时
已经是 `U+FFFD` 替换字符，服务端会判定「值不合法」，得到的是**假故障**。可靠做法：

- 能用 ASCII 就用 ASCII；
- 必须中文时，用 Python（源码里写 `\uXXXX` 转义，纯 ASCII）生成 UTF-8 的 body 文件，
  再 `curl -d @file`；
- 排查时**看 `hex()` 输出，不要看终端回显** —— 终端显示的中文同样不可信。

`remindee` 只有 `黄傲` / `陈婷婷` 两个中文取值，本分区的断言**必须**走上述方式。

## 九、明确不做

以下**不在本次范围**，写在这里是为了避免实施中被「顺手做了」或日后被重新提出：

1. **主动外发通知**（邮件 / 短信 / 企业微信）。架构不支持：无账号体系（不知道发给谁）、
   内网不出网、无后台定时进程。设计方案第八部分 Phase 2 的「邮件通知和提醒」属于未来的
   独立课题，与本模块无关。
2. **周期 / 重复提醒**（每天、每周）。没有调度进程，重复规则只能靠查询时现算，
   复杂度远大于收益。
3. **完成时间的记录**。只存布尔量。
4. **「今日」与「已逾期」的区分**。需求方明确要求两者同一条规则（都标红）。
5. **关联工单 / 需求**。本模块与其它模块零关系。
6. **提醒人的动态候选人名**（会议纪要那套 `PersonSelect`）—— 明确改为固定下拉。
7. **列表内联编辑提醒内容**。只有「已完成」勾选是破例，文本仍走编辑页。
8. **种子数据加演示提醒** —— 保持冒烟脚本依赖的数据基线。

## 十、已知的既有事实（供实施者参考）

### 10.1 断言基线是 181，不是 148

`main` 在 2026-10-13 合并了来自 GitHub 的另一条开发线（提交人字段 + 枚举扩展 + 列表筛选，
merge `ad03284`），断言数由 **119 → 181**（会议纪要/附件那轮 +29，提交人那轮 +33）。
本模块在此基础上 +17 → **198**。

### 10.2 枚举与「单一来源」的现状

`src/types/index.ts` 目前已有：`SYSTEM_OPTIONS`（6）、`WORK_ORDER_STATUS_OPTIONS`（**5**：
新建/已处理/已关闭/处理中/待优化）、`NODE_OPTIONS`（**7**：方案中/开发中/测试中/测试完毕/
已合并/已发布/**退回**）、`SUBMITTER_OPTIONS`（黄傲/陈婷婷）、`YES_NO_OPTIONS`。

`src/lib/server/helpers.ts` 把前四者转发为 `SYSTEMS` / `WORK_ORDER_STATUSES` / `NODES` /
`SUBMITTERS` 供接口层 `includes` 校验 —— `REMINDEES` 照此追加。

### 10.3 Windows 上的坑（会被本模块踩到的）

- **dev server 运行时会锁 `.next`** → `npm run build`、`prisma generate` 报 EPERM，**先停服**。
- dev 的编译队列是串行的，一次编译被中断会让**后续所有请求一起卡住**（端口还在 LISTENING
  但任何页面都不返回）。处理：`netstat -ano | findstr :3000` 拿 PID → `taskkill /F /PID <PID>`。
- 控制台中文会按 GBK 损坏（见 7.2）。

### 10.4 `prisma/seed.ts` 的一个既有缺陷（顺带修）

`seed.ts` 目前只 `deleteMany` 了 `requirement` 和 `workOrder`，**没有清 `meeting` /
`meetingAttachment`** —— 也就是说 CLAUDE.md 里「`db:seed` 会先清空现有数据」这句从会议纪要
上线起就不准确了。本模块实施时一并补上 `meeting` / `meetingAttachment` / `reminder` 的
`deleteMany`，并按 CLAUDE.md 的现状确认该句表述。

### 10.5 git 需要走本地代理（仅在本机需要联网时）

本机到 `github.com:443` 不通（443 被挡），但本机运行着代理客户端（`127.0.0.1:7897`）。
需要联网的 git 操作要临时带参数（**不写进仓库配置**，按用户决定）：

```bash
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 <命令>
```

## 十一、未经验证的假设

实施时**如发现与实际不符，先停下来报告，不要硬绕**。

1. **提醒不需要主动推送，用户接受这个形态**。
   依据：需求方在澄清时选择了「独立新建的提醒条目 + 首页卡片显示未完成条数」，
   而非外发通知。若实际期望是「到日子自动通知到人」，本方案从根上不成立，须重新设计。

2. **部门就是两个人（黄傲 / 陈婷婷），名单固定**。
   依据：`SUBMITTER_OPTIONS` 已是 `as const` 两人硬编码。若人员变动频繁，
   `REMINDEE_OPTIONS` 每次都要改代码，需要改为维护型数据（那就得先改设计文档）。

3. **数据量小（数百至数千条），前端过滤与本地计数够用**。
   依据：与工单/需求/会议并列的部门内部工具。若提醒量级到万条以上，
   §5.2 的「前端过滤」与 §5.4 的「本地计数」都要改成下推 + 计数接口。

4. **`rowClassName` + `.reminder-row-overdue > td { color }` 能盖住 antd v5 的单元格配色**。
   **未实测**。若被主题 token 覆盖，退路是改用 `columns[].render` 逐列包
   `<Typography.Text type="danger">`（代价是列多一些样板代码，效果等价）。

5. **首页卡片读 store 不会出现「0 条 → N 条」的闪烁**。
   依据：store 有 `remindersLoaded` 标记，未加载时显示普通文案即可规避。**未实测**。
