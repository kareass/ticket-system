## 一、目标与规则

把「需求ID」从**必填**改为**选填**，但**仅限手工新建/编辑需求的场景**。

| 场景 | `requirementId` | 说明 |
|------|-----------------|------|
| 工单转需求（`work-order-sync` 三条路径） | **必填**（不变） | 转出的需求必须可追踪 |
| `POST /api/requirements` 带 `workOrderId` | **必填** | 它本质就是转需求；且前端表单未暴露该字段，UI 上走不到 |
| `POST /api/requirements` 不带 `workOrderId` | **选填** | 手工新建 |
| `PUT /api/requirements/:id` | **选填**；传 `""` = 清空 | 编辑 |

**`src/lib/server/work-order-sync.ts:26-33` 一行不改** —— 它是「转需求必须有编号」这条业务
不变量的唯一权威实现处，其余五处（前端弹框按钮禁用/前置校验、工单表单跨字段校验、
工单 POST 预检、convert 路由）都只是它的重复前置，本次也一概不动。

## 二、为什么不能只改 schema

去掉必填的字面改动很小，但直接改会踩三个坑，必须一并处理：

### 2.1 空串会伪装成「撞号」

SQLite 的 `UNIQUE` 索引中 **NULL 互不相等，可以有多条；但空字符串只允许一条**。
实测：

```
两条 NULL + 一条 '' → OK
再加第二条 ''      → UNIQUE constraint failed
```

本项目 `asTrimmed` 会把 `"   "` 归一成 `""`，而空串是**会落库的**（现有代码里
`data.requirementId = requirementId`，只有 `undefined` 才不写该列）。若不归一化，
**第二条无编号的需求会被 P2002 拦成「需求ID 已被占用，请更换。」** —— 一个语义
完全错误的 409，而且用户完全无从理解。

**要求：所有写入点必须把空串显式归一为 `null`。**

项目里已有正确范式可抄：`workOrderId String? @unique`（schema 第 62 行）就是
「可空唯一」的现存先例，且写入侧统一用 `|| null` / `...(v ? { v } : {})` 归一化，
库里 0 条空串。

### 2.2 有一处代码会直接崩

`src/app/requirements/page.tsx:79` 的关键字搜索：

```tsx
req.requirementId.toLowerCase().includes(kw) ||
```

该字段一旦为 `null`/`undefined`，`.toLowerCase()` **抛 TypeError，整页白屏**。
同页其它字段都写了 `(req.title ?? "")` 兜底，唯此处没有。

### 2.3 出参未做空值归一

`src/lib/server/helpers.ts:177` 的 `toRequirementJson` 是 `requirementId: r.requirementId`
直通，因为字段原本不可空。工单侧同一函数里的对应行是 `clean(wo.requirementId)`
（null → undefined）。需与工单侧对齐。

## 三、改动清单

### 3.1 数据层

| 文件:行 | 改动 |
|---------|------|
| `prisma/schema.prisma:48` | `requirementId String @unique` → `String? @unique`，并**生成新迁移** |

**迁移生成方式**：项目现有 3 个迁移均为 `prisma migrate dev` 生成的 SQL（含
`-- RedefineTables` 重建表样板）。SQLite 不支持直接改列约束，**Prisma 会重建
`Requirement` 表**（建新表 → INSERT SELECT → DROP → RENAME），原有数据随之搬运。

> ⚠️ `prisma migrate dev` 在检测到 schema 漂移时会**交互式询问是否重置数据库**。
> 实施时若出现该提示，**必须中止并回报**，绝不能让重置发生。默认情况下本库
> 与迁移记录同步（3 条 `_prisma_migrations` 均已 finish），不应触发重置。

### 3.2 后端

| 文件:行 | 改动 |
|---------|------|
| `src/app/api/requirements/route.ts:69` | 删掉无条件必填校验；**仅在带 `workOrderId` 时**仍要求非空 |
| `src/app/api/requirements/route.ts:126` | `requirementId: requirementId as string` → 条件展开，空串落 `null`（**这是防「一条空串」409 的关键一处**） |
| `src/app/api/requirements/route.ts:150` | 回写工单那处不动：该分支要求 `workOrderId` 存在、且已强制要求编号非空，`as string` 断言仍成立 |
| `src/app/api/requirements/route.ts:159-161` | 409 分支加非空判断：只有非空值碰撞才报「已被占用」 |
| `src/app/api/requirements/[id]/route.ts:75` | `""` 语义由「400 不能为空」改为「清空（落 `null`）」 |

**PUT 的三态语义**（与项目既有契约一致）：

- `undefined`（未传）→ 不改该字段
- `""`（显式清空）→ 落 `null`
- 非空 → 改名；与现值不同才触发改名侦测

**清空时不动来源工单**：沿用既有写法即可 —— `newRequirementId` 在被清空时为空串，
第 163-168 行的 `if (newRequirementId && existing.workOrderId)` 因空串为假而自然跳过，
**工单上登记的编号得以保留**，与项目既有的「删除需求时保留工单编号、便于按原编号重转」
保持一致。实施后需用断言锁住这一行为。

## 六、数据安全（用户明确要求的最高优先级）

本次改动**会重建 `Requirement` 表**，是本项目迄今对数据风险最高的一次操作。
以下步骤为**强制**，不得省略、不得合并、不得跳步。

### 6.1 迁移前

1. **停服** —— 服务运行中锁住 `.next` 且可能持有数据库连接
2. **备份数据库**：`npm run db:backup`，并记下备份文件名
3. **导出迁移前快照**：把 `Requirement` 全表所有字段导出为可逐行比对的文本
   （建议按 `id` 排序，包含 `id / requirementId / date / title / content / system /
   developmentDays / currentNode / isUrgent / isReleased / releaseDate / remark /
   workOrderId / createdAt / updatedAt`）
4. **记录行数与校验值**：行数 + 全表内容的哈希

### 6.2 迁移后

5. **再用同样的方式导出全表**，与 6.1 的快照**逐行逐字段比对**，确认：
   - 行数一致
   - 每行每个字段的值一致（尤其 `requirementId`、`workOrderId`、时间戳）
   - `PRAGMA integrity_check` 返回 `ok`
6. **比对结果必须完整贴出**，不能只说「没问题」

### 6.3 失败回滚

任何一步比对不一致，立即：
1. 停服
2. 用 6.1 的备份文件覆盖 `prisma/dev.db`
3. 重新启动并确认数据恢复
4. 回报，不继续

### 6.4 迁移后还要验证

7. **`api:smoke` 全量重跑**（读写了数据库，需确认无残留、无脏值）
8. **确认没有产生空串**：`SELECT COUNT(*) FROM Requirement WHERE requirementId = ''` 应为 0
9. **确认没有意外 NULL**：现存 15 条数据的编号应全部保留
