# 四川物流工单系统 — 部署指南

> 适用版本：v1.0.0（环节7 交付）
> 部署形态：单个 Node.js 进程（Next.js 全栈，前后端一体）。
> Linux 服务器用 pm2 守护 + Git 拉取更新（第二、三节）；Windows 本地 / 内网单机见第四节。
>
> **目标机不能上外网？** 请改用 → [内网部署方案.md](./内网部署方案.md)（离线整包投递，目标机只需装 Node.js）。

---

## 一、环境要求

| 组件 | 版本 | 说明 |
|------|------|------|
| Node.js | **18.17 及以上**（`package.json` 已声明 `engines`） | 运行环境，推荐 20 LTS |
| npm | 随 Node 附带 | 项目含 `package-lock.json`，使用 `npm ci` 保证依赖一致 |
| Git | 任意近期版本 | 服务器拉取代码（Windows 本地运行可不装） |
| 数据库 | SQLite（默认，零配置）或 PostgreSQL 14+ | 见第五节 |
| pm2 | 最新 | Linux 后台守护进程，可选但强烈建议 |

> 磁盘/内存参考：项目含 `node_modules` 约 500MB，构建期内存峰值约 1GB。

## 二、首次部署（Linux 服务器）

```bash
# 1. 拉取代码到目标目录
sudo mkdir -p /opt/scwos && sudo chown "$USER" /opt/scwos
git clone <内网 Git 地址> /opt/scwos
cd /opt/scwos

# 2. 生成并填写配置文件（SQLite 场景可直接用默认值）
cp .env.example .env
vi .env                      # 至少确认 DATABASE_URL

# 3. 一键部署
bash deploy.sh
```

`deploy.sh` 会依次完成：环境检查 → `git pull` → 校验 `.env` → `npm ci` → `prisma generate` + `prisma migrate deploy` → `npm run build` → `pm2 reload/start`。
脚本是**幂等**的，重复执行即为「更新发布」。

首次执行前若 `.env` 不存在，脚本会自动从模板生成并中止，提示你填写后重跑 —— 这是有意设计，避免用错数据库。

## 三、日常更新发布（Linux 服务器）

```bash
cd /opt/scwos
bash deploy.sh                # 拉代码 + 装依赖 + 迁移 + 构建 + 平滑重载
```

指定分支/进程名：

```bash
DEPLOY_BRANCH=develop APP_NAME=scwos-dev bash deploy.sh
```

**回滚**：

```bash
git log --oneline -5           # 找到上一个可用提交
git checkout <commit>
bash deploy.sh                 # 重新构建并重载（会切回 detached HEAD，随后 git checkout main 复位）
```

## 四、Windows 部署（本地 / 内网单机）

适用场景：本机试用、部门内一台常开的 Windows 机器当内网服务器。**无需安装数据库**（SQLite 零配置）。

### 4.1 环境准备

1. 安装 **Node.js 18.17+**（推荐 20 LTS）：官网下载 `.msi`，安装时保持勾选 *Add to PATH*。
2. 安装 **Git for Windows**（可选）—— 只在本机跑服务可以不装；要拉代码更新才需要。
3. 打开「命令提示符」或「PowerShell」，确认：

```powershell
node -v     # 应输出 v18.17.0 及以上
npm -v
```

> 若提示「不是内部或外部命令」，说明 Node 未加入 PATH，重装并勾选该选项，或重启终端。

### 4.2 首次部署

把项目目录换成本机实际路径（路径含空格/中文时**务必加引号**）：

```powershell
cd "E:\ai\claude code\四川物流工单系统"

npm ci                        # 安装依赖（自动执行 prisma generate）
Copy-Item .env.example .env   # 生成配置；Git Bash 下用 cp .env.example .env
npx prisma migrate deploy     # 建表
npm run db:seed               # 可选：写入演示数据（注意：会先清空现有数据）
npm run dev                   # 启动
```

浏览器打开 **http://localhost:3000** 即可。

> PowerShell 若提示「禁止运行脚本」，是执行策略限制，与项目无关。改用「命令提示符(cmd)」执行，或先运行
> `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`（仅需一次）。

### 4.3 日常启动与停止

**开发模式**（改代码自动生效，启动稍慢）：

```powershell
cd "E:\ai\claude code\四川物流工单系统"
npm run dev
```

**生产模式**（响应更快，适合给同事用）：

```powershell
cd "E:\ai\claude code\四川物流工单系统"
npm run build                 # 打包；首次和每次更新代码后需执行一次
npm run start                 # 启动
```

两种模式都访问 http://localhost:3000。

- 启动服务的**终端窗口必须保持打开**，关掉窗口即等于停服。
- 停止服务：在该窗口按 **Ctrl + C**。

> **选哪个？** 只把系统**拿来用**，请用**生产模式** —— 页面是预编译好的，实测 6~300ms 打开。
> 开发模式会在你**首次进入每个页面时现场编译**（3000+ 模块，实测 1.5~6.6 秒），所以「新建」「编辑」这类页面头一次点开明显发卡，之后才变快。改代码调试时才需要 dev 模式。

### 4.4 做成双击即启动的快捷方式（推荐给不熟悉命令的同事）

新建文本文件，改名为 `启动系统.bat`，内容如下（路径改成实际路径）：

```bat
@echo off
chcp 65001 >nul
cd /d "E:\ai\claude code\四川物流工单系统"
echo 正在启动四川物流工单系统，请勿关闭本窗口...
npm run start
pause
```

双击即可启动；窗口保持打开就是服务运行中，关窗口即停服。

> 注意：该方式依赖已完成 `npm run build`。首次使用、或代码更新后，需先手动执行一次 `npm run build`。

### 4.5 让局域网内其他同事访问

服务默认监听所有网卡，同事用你的 IP 即可访问：

```powershell
ipconfig                      # 找到「IPv4 地址」，如 192.168.1.100
```

同事浏览器打开 `http://192.168.1.100:3000`。

若无法访问，需放行防火墙端口（**管理员身份**运行 PowerShell，只需执行一次）：

```powershell
New-NetFirewallRule -DisplayName "SCWOS 3000" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow
```

### 4.6 开机自动启动（可选）

- **简单做法**：把 4.4 的 `.bat` 放入「启动」文件夹（`Win + R` 输入 `shell:startup`），登录后自动运行。
- **正规做法**：用 [NSSM](https://nssm.cc/) 把 Node 注册为 Windows 服务，开机即启、崩溃自动重启，且无需登录桌面。

### 4.7 Windows 上的注意事项

| 现象 | 原因与处理 |
|------|-----------|
| `npm run build` 报 `.next` 相关 **EPERM / 文件被占用** | dev server 正运行并锁住了 `.next`。先 Ctrl+C 停掉再构建；若需在 dev 运行期间验证构建，用隔离目录：`$env:NEXT_DIST_DIR=".next-build"; npm run build`（cmd 下为 `set NEXT_DIST_DIR=.next-build&& npm run build`），完事后删除 `.next-build` |
| `prisma generate` 报 EPERM | 同上：运行中的 dev server 占用查询引擎 dll。停服后重跑 |
| 启动报 `EADDRINUSE`（端口被占用） | `netstat -ano \| findstr :3000` 找到末尾的 PID，再 `taskkill /F /PID <PID>`；或改 `.env` 里的 `PORT=3001` 重新启动 |
| 中文乱码 | 用 PowerShell / 新版命令提示符；`.bat` 中已加 `chcp 65001` |
| 路径报错「系统找不到指定的路径」 | 路径含空格或中文未加引号，`cd` 后要用双引号包住整个路径 |
| 换机器/迁移数据 | 复制 `prisma\dev.db` 一个文件即可，**这就是全部数据** |

> Windows 下 `bash scripts/db-init.sh` 需在 Git Bash 中运行；直接用 npm 脚本更省事：
> `npx prisma migrate deploy`（建表）、`npm run db:seed`（演示数据）、`npx prisma migrate reset --force`（重置清库）。

## 五、数据库配置

### 方案 A：SQLite（默认，适合小规模内部使用）

```env
DATABASE_URL="file:./dev.db"
```

- 数据库文件位于 `prisma/dev.db`，**该文件即全部数据，务必备份**。
- Linux 备份：`cp prisma/dev.db "backup/dev-$(date +%F).db"`（建议配 crontab 每日一次）。
- Windows 备份：直接复制 `prisma\dev.db` 到其他目录。

### 方案 B：PostgreSQL（数据量大或需高可用时）

```env
DATABASE_URL="postgresql://USER:PASSWORD@HOST:5432/DBNAME?schema=public"
```

切换后需同步修改 `prisma/schema.prisma` 中 `datasource db` 的 `provider` 为 `postgresql`（当前为 `sqlite`），然后：

```bash
npx prisma migrate deploy      # 应用迁移建表
```

> 注意：SQLite 与 PostgreSQL 的迁移历史不通用，切换数据库属于一次性数据迁移动作，建议在项目尚未积累正式数据时完成。

### 数据库初始化脚本

```bash
bash scripts/db-init.sh                 # 建表（应用全部迁移）—— 生产首次部署用
bash scripts/db-init.sh --with-seed     # 建表 + 写入演示数据（会先清空现有数据）
bash scripts/db-init.sh --drop          # 重置数据库并重新迁移（二次确认，清空全部数据）
```

## 六、部署检查清单

部署前 / 部署后逐项确认。

### 6.1 部署前（在服务器执行一条命令即可）

```bash
npm run check:env
```

该脚本逐项输出 `[OK]/[WARN]/[FAIL]`，任一 `FAIL` 时以非 0 退出。检查项：

| # | 检查项 | 期望 |
|---|--------|------|
| 1 | Node.js 版本 ≥ 18 | OK |
| 2 | 项目目录可写（构建与 Prisma 生成需要） | OK |
| 3 | `node_modules` 已安装 | OK |
| 4 | `.env` 存在 | OK（生产必填） |
| 5 | `DATABASE_URL` 已配置且格式可解析 | OK |
| 6 | SQLite 场景下数据库文件存在 | OK / WARN（首次部署前允许 WARN） |
| 7 | Prisma Client 已生成 | OK |
| 8 | 数据库可连接且表结构就绪（回显工单/需求条数） | OK |
| 9 | 端口 `PORT`（默认 3000）可用 | OK / WARN（服务已在运行则属正常） |

> 安全说明：脚本只回显 `DATABASE_URL` 的**协议 + 主机 + 库名**，不会输出账号密码。
> Windows 同样适用：`npm run check:env` 是排查「起不来」的第一手段。

### 6.2 部署后验证

| # | 验证项 | 方法 | 期望 |
|---|--------|------|------|
| 1 | 进程存活 | `pm2 status`（Windows 直接看终端窗口） | `online`，重启次数无异常增长；Windows 下终端无报错且未退出 |
| 2 | 端口监听 | `ss -lntp \| grep 3000`（Windows：`netstat -ano \| findstr :3000`） | 有 LISTEN |
| 3 | 首页可达 | 浏览器打开 `http://<IP>:3000` | 显示系统首页与两张功能卡片 |
| 4 | 工单列表 | 打开「工单管理」 | 列表加载，无报错弹窗 |
| 5 | 需求列表 | 打开「需求管理」 | 同上 |
| 6 | 写操作 | 新建一条工单并提交 | 提交成功提示，列表出现新记录，刷新后仍在 |
| 7 | 转需求 | 对该工单点「转需求」 | 弹框内填写需求ID（如 `R-2026-004`）→ 确认 → 需求列表出现同编号需求，「关联需求」列变蓝色标签 |
| 8 | 接口健康 | `curl -s http://127.0.0.1:3000/api/work-orders` | 返回 JSON 数组 |
| 9 | 持久化 | `pm2 restart`（Windows：Ctrl+C 后重新启动）后刷新页面 | 数据仍在 |
| 10 | 日志无异常 | `pm2 logs --lines 50`（Windows 看终端输出） | 无未捕获异常堆栈 |

### 6.3 接口冒烟（可选，更严格）

后端 API 全套自动化断言（107 项，含数据自清理）：

```bash
npm run api:smoke
```

> 需服务已在 3000 端口运行；运行结束会自动清理本轮测试数据。

## 七、常见问题 FAQ

**Q1：`npm ci` 报错或依赖装不上？**
确认 Node 版本 ≥ 18.17（`node -v`）。内网无外网时需配置 npm 私服：`npm config set registry http://<私服地址>/`，或使用离线镜像拷贝 `node_modules`。

**Q2：`prisma migrate deploy` 报 `P1001: Can't reach database server`？**
PostgreSQL 场景：确认库已启动、`.env` 中主机/端口/账号正确、服务器防火墙放行 5432。SQLite 场景一般不会出现，多为 `DATABASE_URL` 路径写错。

**Q3：启动后浏览器打不开页面？**
① `pm2 logs`（Windows 看终端窗口）看是否启动失败；② 确认端口：`PORT` 未设置时默认 3000；③ 服务器安全组/防火墙放行该端口；④ 仅内网访问时确认客户端在同一网段。Windows 局域网访问见 4.5。

**Q4：页面能开但列表一直转圈、控制台报 500？**
多为数据库未初始化。执行 `npm run check:env` 定位；若提示表结构不就绪，执行 `npx prisma migrate deploy`。

**Q5：`npm run build` 失败，报 `.next` 相关 EPERM / 文件被占用（Windows）？**
开发服务器正在运行会占用 `.next` 目录。生产构建请先停掉 dev server；如需在 dev 运行期间做隔离构建验证，可用 `NEXT_DIST_DIR=.next-build npm run build`（已内置支持，`.next-build` 已被 git 忽略）。

**Q6：构建期内存不足（OOM，常见于 1GB 小内存机）？**
`NODE_OPTIONS=--max-old-space-size=1536 npm run build`，或临时加 swap。

**Q7：提示「需求ID 已被占用」？**
需求编号全局唯一。换一个编号，或到需求列表确认这条需求是否已经建过。转需求时弹框里填的编号若已存在即报此提示。

**Q8：想清空演示数据、重新开始？**
`npx prisma migrate reset --force`（会清库并重放迁移）或 `bash scripts/db-init.sh --drop`。

**Q9：如何修改端口？**
`.env` 中设置 `PORT=3001`，重新启动（Linux 为 `bash deploy.sh`，Windows 重跑 `npm run start`）。

**Q10：pm2 开机自启？**
`pm2 startup` 生成命令并按其提示执行一次，随后 `pm2 save`。Windows 见 4.6。

**Q11：`.env` 要不要提交到 Git？**
**不要**。`.env` 已在 `.gitignore` 中；仓库只保留 `.env.example` 模板。API 密钥类信息不得写入任何文档或提交记录。

**Q12：点「新建工单」「编辑」转半天才出来？**
多半是跑在**开发模式**下：dev 会在首次进入每个路由时现场编译，单次 1.5~6.6 秒（详见 4.3 的说明）。解决：改用生产模式 —— `npm run build` 后 `npm run start`，实测页面 6~300ms。

**Q13：服务突然整体无响应（连接口都不回）？**
dev 模式的编译队列是串行的，一次编译被中断（例如请求超时断开、编辑器保存触发连续重编译）可能让后续请求全部排队卡住。表现是端口还在监听但任何页面都不返回。处理：结束该 node 进程后重新启动（Windows 见 4.7 的 `taskkill` 用法）。
