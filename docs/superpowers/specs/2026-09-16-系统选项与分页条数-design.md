export const SYSTEM_OPTIONS = ["WMS", "ERP", "TMS", "SCM", "追溯中心", "其他"] as const;

## 二、后端 system 枚举兼容保险

### 2.1 要解决的问题

后端对 `system` 做硬校验 `SYSTEMS.includes(system)`，而前端表单保存时**无条件
下发全部字段**。两者叠加的后果是：

> **一旦删除某个系统选项、而库里又有用该选项的存量记录，那些记录的编辑页就再也
> 保存不了**——报 400，且同一笔请求里改的其它字段也一起不落库（校验在事务之前）。

本项目的用户手册 7.1 节把「增删下拉选项」写成了常规管理员操作，所以这个坑会重复踩。

### 2.2 规则

**提交值与库中现值相同时，跳过枚举校验；不同时才校验。**

实现落在 2 个 PUT 路由：

- `src/app/api/work-orders/[id]/route.ts`
- `src/app/api/requirements/[id]/route.ts`

现在的写法：

```ts
if (body.system !== undefined) {
  const system = asTrimmed(body.system);
  if (!system || !SYSTEMS.includes(system)) {
    errors.push(`system 须为以下之一：${SYSTEMS.join(" / ")}。`);
  } else data.system = system;
}
```

改为：

```ts
if (body.system !== undefined) {
  const system = asTrimmed(body.system);
  // 与库中现值相同 → 视为未变更，跳过枚举校验。
  // 这样管理员删除某个系统选项后，存量记录的其它字段仍可正常保存；
  // 但把值改成枚举外的**新**值仍会被拦下。
  if (!system) {
    errors.push(`system 须为以下之一：${SYSTEMS.join(" / ")}。`);
  } else if (system !== existing.system && !SYSTEMS.includes(system)) {
    errors.push(`system 须为以下之一：${SYSTEMS.join(" / ")}。`);
  } else {
    data.system = system;
  }
}
```

`existing` 指路由中已经查出的当前记录（PUT 路由本来就要先查记录以决定 404）。

### 2.3 行为对照

| 场景 | 现在 | 改后 |
|------|------|------|
| 存量记录（system 为已删除的枚举值）改备注，表单整份下发 | **400，全笔不落库** | ✅ 200 正常保存 |
| 把 system 改成枚举外的**新**值 | 400 | ✅ 仍然 400 |
| 把 system 从旧值改成枚举内的合法值 | **400** | ✅ 200 |
| 创建新记录时传枚举外的值（POST） | 400 | ✅ 不变，仍 400 |

**POST 路由不改**：新建记录不可能「保持原值」，没有这个问题。

### 2.4 本次不覆盖「工单状态」（已知遗留）

`status` 字段存在**完全相同**的隐患，且用户手册同样写明它可增删。
经确认本次**只改 system**，不改 status。

**这是本次引入的已知偏离，必须记录：**

> `src/app/api/work-orders/[id]/route.ts` 的 `status` 校验仍是硬校验。
> 若日后删除「新建 / 已处理 / 已关闭」中的任一项且库中有存量记录，
> 那些工单的编辑页将无法保存。届时需套用与 system 相同的规则。

### 2.5 验证方式（重要）

**纯 HTTP 造不出「非法存量值」**——API 不允许创建 system 非法的记录。因此核心场景
无法用 `api-smoke.mjs` 覆盖。验证分两层：

1. **自动化回归**：在 `scripts/api-smoke.mjs` 补 2 条断言，防止改动把正常路径改坏：
   - 传**未变更**的合法 system → 仍 200（回归，确保新分支没把正常路径吃掉）
   - 传**枚举外的新**值 → 仍 400（确保放宽没有过头）
2. **核心场景手动验证**（可复现步骤，一次性执行）：
   ```bash
   # 1. 先记下目标需求的原 system 值，备用还原
   sqlite3 prisma/dev.db "SELECT requirementId, system FROM Requirement LIMIT 1;"
   # 2. 把它的 system 改成已删除的 OMS，模拟存量脏数据
   sqlite3 prisma/dev.db "UPDATE Requirement SET system='OMS' WHERE requirementId='<上一步查到的ID>';"
   # 3. curl 发一个「不传 system」的 PUT（只改备注）
   #    期望：200，备注已改，且 system 仍为 OMS
   # 4. curl 发一个「传 system='OMS'」的 PUT
   #    期望：200（与现值相同 → 跳过校验），system 仍为 OMS
   # 5. curl 发一个「传 system='不存在的系统'」的 PUT
   #    期望：400
   # 6. 还原：把 system 改回第 1 步记下的原值
   ```

   > 该需求必须**指定具体的 `requirementId`**（运行时由上一步查出），
   > 且第 6 步的还原不能漏——否则会在库里留一条脏数据。

## 三、每页条数选择器

### 3.1 现状

两个列表页的 pagination 配置完全相同，且 `showSizeChanger` 被**刻意关掉**：

```tsx
pagination={{
  pageSize: 10,
  showSizeChanger: false,
  showTotal: (total) => `共 ${total} 条`,
}}
```

`ProTable` 对 `pagination` 是**纯透传**（它落在 `...rest` 里铺给 antd Table），
不做任何处理。项目里**不存在**任何 pageSize 持久化。

### 3.2 实现位置：放进 ProTable

把每页条数交给 `ProTable` 统一管理，而不是在两个页面各写一遍。

理由：ProTable 的职责本就是「列表容器 + 列宽列序记忆」，分页记忆属于同一职责；
两处 pagination 字面量完全相同，本就是重复。

ProTable 接管：

- 默认 `pageSize: 10`
- `showSizeChanger: true`
- `pageSizeOptions: ["10", "20", "30", "50", "100"]`（含 `10`，因为 antd 的下拉
  要求当前值在列表中才能正常高亮）
- 持久化到 `protable:pageSize:<layoutStorageKey>`

**合并语义**：ProTable 先铺自己的默认值（`pageSize` / `showSizeChanger` /
`pageSizeOptions`），再把调用方传入的 `pagination` 对象铺在其上——
**调用方同名字段优先**。因此页面仍可传 `showTotal`，也可以在将来某张表上
单独关掉选择器。若调用方显式传了 `pageSize`，则以调用方为准且不启用持久化
（避免两处状态打架）。

两个列表页相应删掉自己的 `pageSize` 与 `showSizeChanger`，只保留 `showTotal`。

### 3.3 为何用独立 localStorage key

**不并入**已有的 `protable:layout:<key>` 存档。

那个存档驱动着「还原默认列布局」按钮的显隐与语义（`isDefaultLayout` 只比较
order 与 widths）。若把 pageSize 并进去，仅仅改过条数的用户会看到该按钮出现，
点下去还会把条数一并重置——按钮名不副实。

两件事分开存，各管各的：

| key | 内容 | 对应 UI |
|-----|------|---------|
| `protable:layout:<key>` | `{ order, widths }` | 列拖序、列宽、「还原默认列布局」按钮 |
| `protable:pageSize:<key>` | `10` \| `20` \| `30` \| `50` \| `100` | 底部条数选择器 |

**读档必须做合法性校验**：只接受 5 个档位内的值，否则退回 10。防止篡改存档
或旧数据把表格置于异常状态（与 `protable:layout` 恢复时过滤不存在的列 key 是同一
思路）。

### 3.4 与既有决策的一致性

上一次改动（列表排序）明确决定「**不做受控分页**，排序后停留当前页码」。
本次**不推翻该决策**：

- 只接管 `pageSize`，**不接管 `current`**
- 排序行为完全不变，仍然停留当前页
- 改变条数时 antd 会自行把页码重置到第 1 页，这是 antd 的默认行为，符合直觉

### 3.5 两表独立

每张表各记各的（key 里带 `layoutStorageKey`），工单页设成 50 不影响需求页。
