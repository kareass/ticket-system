## 6.3 性能优化

| 项 | 措施 |
|----|------|
| 列表分页 | 两列表均 10 条/页（前端分页），避免一次渲染全量 |
| 数据缓存 | store 增加「已加载」标记：页面来回切换不重复请求；工具栏「刷新」按钮 `force=true` 手动拉取 |
| 单条拉取 | 编辑页优先用已加载缓存，仅在缺失时才 GET 单条，减少一次请求 |
| 查询下推 | 列表筛选（system/keyword/currentNode）由后端 `where` 承担，前端仅在已取数据上做轻量过滤 |

**实测响应时间**（dev 模式，各 5 次采样）：

| 端点 | 耗时 |
|------|------|
| `GET /api/work-orders` | 0.021–0.027 s |
| `GET /api/requirements` | 0.022–0.027 s |
| 页面 `/work-orders` | 0.081–0.098 s |
| 页面 `/requirements` | 0.067–0.092 s |

均远低于 1s 心理阈值，判定达标。

## 6.4 Bug 列表与修复记录

| # | 现象 | 根因 | 修复 | 回归 |
|---|------|------|------|------|
| B1 | 编辑工单时「清空备注」不生效（旧值仍在） | 前端 `remark: undefined` 被 `JSON.stringify` 丢弃，后端收不到 key 就不置空 | 表单改为显式下发 `""`；后端 PUT 收到 key 时 `"" → null` | 冒烟「备注清空下发生效（回归）」 |
| B2 | 编辑需求时「清空标题/内容」不生效 | 同 B1（`title/content` 用 `|| undefined` 丢字段） | 表单显式下发 `""`；后端 PUT 置 null | 冒烟「标题清空下发生效（回归）」 |
| B3 | 空字符串入库（`""` 而非 `null`），列表展示与「有值/无值」判断口径不一致 | 创建接口对可选字段用 `!== undefined` 判断，`""` 被当作有值写入 | 创建接口改用真值判断，`"" → null` | 冒烟创建/清空用例 |
| B4 | 列表页来回切换重复请求后端 | 每次挂载都无条件拉取 | store 增加 `Loaded` 缓存标记 + 手动刷新 | 手动验证（网络面板） |
| B5 | 编辑页加载态 `Spin tip` 触发 antd v5 告警 | 未使用嵌套写法 | 改为 `Spin` + 文案两行 | 目视 |

### 第四轮验收反馈（同上）

| # | 反馈 | 处理 |
|---|------|------|
| F7 | 下拉选项收敛成单一来源 | 全站枚举定义由 8 处收敛到 1 处（`src/types/index.ts`）。此前「工单状态」重复 4 份、「系统」5 份、「是/否」3 份、「需求节点」2 份，改漏一处就会出现「表单能选、后端拒绝」或列表与表单选项不一致 |

**F7 具体做法**：数组统一声明为 `as const`，联合类型（`WorkOrderStatus` / `RequirementNode`）由
`typeof ARR[number]` 从数组推导，消除「数组加了一项、类型没跟着改」的可能；配色表改为
`Record<联合类型, string>`，漏加配色直接编译报错；新增 `asSelectOptions()` 收敛 8 处重复的
`.map(v => ({ label: v, value: v }))`。后端 `helpers.ts` 的 `SYSTEMS` / `WORK_ORDER_STATUSES` / `NODES`
改为对同一数组的转发（原 `WORK_ORDER_STATUSES` 是独立硬编码），此后**接口校验与前端下拉不可能再分叉**。

收敛后复验：`npm run typecheck` 零错误；生产构建通过；`npm run api:smoke` **107 项断言全绿**（枚举校验
行为未变，断言数与改动前一致）；两次连跑后数据回到基线。
