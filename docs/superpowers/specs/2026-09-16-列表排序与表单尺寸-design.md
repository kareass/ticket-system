## 一、列表排序

### 1.1 目标

需求列表与工单列表支持按业务字段排序，**触发方式为双击列名**。

### 1.2 为什么不用 antd 内置 `sorter`

antd Table 的排序手势固定为**单击**，且没有提供任何接口可改为双击——它把整个表头
单元格包成一个可点击的排序触发器。要改成双击只能劫持点击事件自行计数，属于对抗框架。

此外本项目有两处具体冲突：

1. `ProTable.tsx:347` 的 `HeaderCell` **无条件覆盖 `onHeaderCell`**，无法借它注入自定义行为。
2. 表头右缘有 6px 的拖宽手柄且带 `z-index: 1`，会遮挡 antd 默认渲染在右侧的排序箭头。

结论：不使用 antd 的 `sorter`，完全自研排序状态与列头。

### 1.3 架构

新增共享模块 **`src/lib/sortRows.ts`**，两个列表页共用：

```ts
type SortOrder = "ascend" | "descend";
type SortState<T> = { field: keyof T; order: SortOrder } | null;

createComparator<T>(field: keyof T, order: SortOrder): (a: T, b: T) => number
```

新增共享列头组件 `src/components/common/SortableHeader.tsx`（与同目录下的
`ProTable` / `EditableChip` / `SystemSelect` 并列），渲染：

- 列名文本
- 双击处理器
- 当前排序指示符（`▲` / `▼`），**画在列名左侧**

指示符必须在左侧：右侧要留给 ProTable 的拖宽手柄，画右侧会被遮住。

### 1.4 枚举字段的序：不另建一套

项目硬规则第 1 条规定「下拉选项只有一个来源：`src/types/index.ts`」。
因此枚举字段的业务顺序**直接取现有数组的下标**，不新增顺序数组：

```ts
NODE_OPTIONS.indexOf(currentNode)            // 方案中=0 … 已发布=4
SYSTEM_OPTIONS.indexOf(system)
WORK_ORDER_STATUS_OPTIONS.indexOf(status)    // 新建=0 …
```

好处：日后调整下拉顺序，排序顺序自动跟随，不会出现两套顺序打架。

### 1.5 字段与比较策略

**需求列表可排序字段**：`date`、`developmentDays`、`currentNode`、`isUrgent`、`isReleased`、`releaseDate`

**工单列表可排序字段**：`date`、`system`、`status`

| 字段 | 比较策略 |
|------|----------|
| `date` | 字符串直接比较——出参是 `YYYY-MM-DD`，字典序等于时间序 |
| `developmentDays` | 数值比较；**null 恒排末尾**（升序降序都排末尾） |
| `releaseDate` | 同 `developmentDays`（未发版者为空，会集中在末尾） |
| `currentNode` / `system` / `status` | 按上文 `indexOf` 下标比较 |
| `isUrgent` / `isReleased` | `false < true`，升序即「否」在前 |

不可排序的列：`需求ID`、`标题`、`内容`、`备注` 等文本列，以及
「来源工单」「关联需求」「操作」这些派生/操作列。

> 备注：需求列表的「系统」列本次不做排序（选择范围时未纳入）。若日后要加，
> 复用 `SYSTEM_OPTIONS.indexOf` 即可，成本极低。

### 1.6 交互

双击列名，三态循环：

```
升序 ▲  →  降序 ▼  →  取消排序（回到默认的创建时间倒序）  →  升序 ▲ …
```

默认状态（未排序）为后端返回的 `createdAt desc`，与现状一致。

### 1.7 排序作用位置与草稿的关系

数据流：`store 全量数据` → `useMemo 前端筛选` → `useMemo 排序` → `.map(drafts.merge)` → `ProTable`

排序**作用在筛选后的已提交值上，位于 `drafts.merge` 之前**：

```tsx
dataSource={sortedRequirements.map(drafts.merge)}
```

已确认的产品决策：**按已提交的值排序**。未提交的内联草稿不参与排序，
因此用户编辑某行时该行不会跳走。代价是改了字段但未提交期间，行的位置与显示的
值会暂时不一致，提交后归位——这与项目「修改需显式提交」的硬规则一致。

### 1.8 明确不做（YAGNI）

- **不重置页码**：排序后停留在当前页码，不改为受控分页。
- **不做后端排序**：数据本就是前端一次全量拉取 + 前端分页，排序下推到 SQL
  用户感知不到差别，却要多改接口、`api.ts`、`store` 三处。
- **不持久化排序状态**：不写入 localStorage（列宽列序的持久化不受影响）。

## 二、表单内容框尺寸

### 2.1 根因：宽度由外层容器决定

`Input.TextArea` 未设宽度，靠撑满父容器。真正的宽度约束是两个表单文件里写死的容器：

```tsx
{/* 限制表单列宽，避免整卡宽度下输入框过长 */}
<div style={{ maxWidth: 640 }}>
```

所以「宽度增加 1/2」的正确改法是改容器，而不是给 TextArea 加 `style.width`。

### 2.2 改动清单

| 位置 | 文件:行 | 现 | 改为 |
|------|---------|-----|------|
| 表单容器（工单） | `WorkOrderForm.tsx:208` | `maxWidth: 640` | `960` |
| 表单容器（需求） | `RequirementForm.tsx:247` | `maxWidth: 640` | `960` |
| 工单内容 | `WorkOrderForm.tsx:242` | `rows={4}` | `rows={8}` |
| 需求内容（工单表单·转需求门控） | `WorkOrderForm.tsx:327` | `rows={3}` | `rows={6}` |
| 工单备注 | `WorkOrderForm.tsx:337` | `rows={2}` | `rows={4}` |
| 需求内容（需求表单） | `RequirementForm.tsx:295` | `rows={3}` | `rows={6}` |
| 需求备注 | `RequirementForm.tsx:359` | `rows={2}` | `rows={4}` |
| 需求内容（列表「转需求」弹框） | `work-orders/page.tsx:391` | `rows={3}` | `rows={6}` |

### 2.3 两点说明

1. **列表「转需求」弹框**里的 `需求内容` 是裸 `Input.TextArea`（不在 `Form.Item` 内，
   也不在 640 容器内），宽度由弹框决定，**因此只翻倍高度、不动宽度**。
2. **容器变宽的连带影响**：撑满容器的 `标题`、`需求ID` 等 `Input` 会一并变宽（符合预期）；
   `WIDTH` 常量控制的固定像素控件（日期、系统、当前节点等下拉框）不受影响，
   不会被拉成整行，与文件注释的原意不冲突。

### 2.4 「高度×2」的口径

用 `rows` 翻倍实现。`rows` 控制可见文本行数，得到约 2 倍的可视高度；
内边距不参与翻倍，所以不是像素级精确的 2 倍。

### 2.5 注释同步

两处注释写明「表单容器统一 640px」，改宽度后必须同步更新，否则注释与代码不符：

- `WorkOrderForm.tsx:74-76`（`WIDTH` 常量上方的说明）
- `RequirementForm.tsx:120-122`
- 以及 `WorkOrderForm.tsx:207` / `RequirementForm.tsx:246` 的行内注释

## 三、必须由用户验证的部分

项目硬规则第 3 条：**UI 改动必须由用户在浏览器中实际验证后才算完成**，
本环境无浏览器自动化。本次需要实测的点：

1. **双击列名能否触发排序**——ProTable 把表头 `children` 包在一个 `draggable` 的 div 里
   （`ProTable.tsx:158-173`），双击事件能否穿透需实测确认。
2. **双击不会误触发拖拽，拖拽也不会误触发排序**——两套手势是否真正分离。
3. **排序指示符没有被右缘拖宽手柄遮挡**（`z-index: 1`，宽 6px）。
4. 表单容器变宽后，各页面布局正常，无横向滚动条溢出。
5. 内容框、备注框的宽高变化符合预期。
